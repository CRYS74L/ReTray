# dev.252：修复临界宽度的反复布局

用户新的 7.882 秒、60 FPS 录屏证明 dev.251 仍有停顿，上一版分段设置窗口宽度的测试不足以证明真实拖拽流畅。本次先逐帧核对录屏：鼠标继续向左，窗口右边缘在一段时间内不变，随后布局跳变；不是简单的客户区短暂晚呈现。

## 确认的原因

宽窗口用 `WorkspaceGrid.ActualWidth - 606` 动态限制侧栏，125% DPI 会把某些列宽舍入到比上限更大的物理像素位置。回归直接复现：窗口 916 DIP，最大侧栏宽 310 DIP，实际却为 310.4 DIP。WPF 在互相冲突的约束下重复测量/排列，临界宽度区域反复接近一秒；字体格式化出现在栈中是反复排版的结果，未据此更换字体。

最大侧栏宽现在向下对齐物理像素，最低约束向上对齐；收起侧栏也使用同一像素对齐宽度。DPI 改变后，在 WPF 传播完新比例后重算约束并结束旧比例的宽度动画。100/125/150/175/200% 下原有 56 DIP 收起宽度保持不变。

另一个确定的重复失效是列表/详情每次宽度变化都创建同样的渐隐 OpacityMask。本次按公式真正依赖的高度、顶部和底部渐隐长度复用冻结画刷；滚动及高度改变仍会更新。没有改变渐隐公式、常态 Acrylic、字体文件、字体脸、字号、字重或 dev.251 的视觉修改。

## 验证

- `--resize-cache-regression` 在旧版断言失败：310.4 超过最大值 310；修复后通过。覆盖六个有问题的临界宽度、布局收敛、等价遮罩复用以及滚动/高度变化更新。
- 相同的 19 设备、600 流量采样、40 历史条目 fixture 连续细步重排 720 次：修复前最大 1600.48 ms、P95 937.32 ms、累计同步耗时 72321.87 ms；修复后最大 55.99 ms、P95 28.73 ms、累计 11506.92 ms。此为代码诊断的同步耗时，不伪称匀速鼠标录屏或 60 FPS 保证。
- 局部四步对照：旧 916/922 DIP 耗时约 2683/1432 ms、布局未在同步调用内完成；修复后四步共 171 ms，实际列宽全部不超过最大值，正常产生布局完成事件。
- Computer Use 标准 drag 经记录确认只有起止点，无法充当匀速输入验收；已停止输入、重置控制连接并在桌面截图中确认控制提示消失，没有继续用它验证本次修复。
- Release 构建 0 警告、0 错误；临界宽度/渐隐缓存回归及原有响应式导航回归通过。
- 最小化材质回归重跑通过：16 轮、229 个有效移动材质帧、0 漏底，常态像素对照与取消路径通过。
- 旧全量自检本次报 14 项，全部来自原有 33 项失败清单，没有新增失败名称；不将这套旧自检称为全量通过。

诊断日志、用户录屏帧和辅助代码位于忽略目录 `runtime-data/resize-followup` 与 `.tools`。所有改动只针对约束与等价渲染资源复用；此前失败的完整旧自检不作为本次通过证据。
